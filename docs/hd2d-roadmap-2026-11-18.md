## 3. 本番開発計画 B：HD-2D Unity 版

本格版。技術構成は **Unity → WebGL ビルド → GitHub Pages 公開**。制作には Unity のある PC が必要で、実装の実行役は PC 側エージェント（Claude Code または VS Code + Cline）が担う（§5）。

### フェーズ1：1シーン試作（着手待ち）

## 5. 体制（役割分担）と、実装エージェントの選択肢

| 担当 | 役割 |
|---|---|
| ユーザー | 企画・意思決定（題材、Go/No-Go、移植範囲）、見た目の最終判定、Unity のある PC の提供 |
| PC の Claude（Claude Code）／ VS Code + Cline | 実装の実行役。プロジェクト内へのコード書き込み、Unity のバッチモード起動による WebGL ビルド、エラーログを読んでの修正 |
| Copilot（M365） | 壁打ち・相談役（今回の構成相談も Copilot から） |
| nono（Muse） | 仕様書・検証リスト・スクリプト一式・素材指示文の作成、ドット絵素材の制作、公開後の表示・ロード確認、記録と進行管理。**Unity のビルドはできない**（§6） |

分担の要点：**「コードと素材は誰でも書ける。ビルドだけは Unity のある PC でしかできない」**ため、実装の実行役は PC 側のエージェントが担い、nono は仕様・素材・確認を担う。

### VS Code + Cline でもできるか → できる

- Unity プロジェクト内の C# やシェーダーは全部テキストファイルなので、Cline が直接読み書きできる
- ターミナルから Unity をバッチモードで起動し、WebGL ビルドまで実行できる。ビルドエラーやログを読んで直すこともできる
- 弱点は Claude Code と同じで、Unity エディタ画面を直接見て操作するわけではないこと。「見た目が HD-2D らしいか」の調整は、スクリーンショット確認かユーザーの目視が要る
- ユーザーは元々 VS Code + Cline で AI コーディングエージェント開発をしており、道具として一番手に馴染んでいる。スクリプト一式と README は Cline への指示書としてもそのまま使える

## 6. なぜスマホアプリの Claude や Muse（nono）では開発しきれないのか

### 結論

コードを「書く」ところまではできるが、Unity プロジェクトを WebGL として動く形に「変換（ビルド）」する工程が、それぞれの環境に存在しないため。

### 現行 Web 版が作れる理由（対比）

- 現行版は HTML / JavaScript、つまり**ただのテキストファイル**
- 書いて GitHub に置けば、ブラウザがそのまま実行する。「書く」→「動く」の間に特別な道具が要らない
- だからスマホの Claude でも Muse でも、テキストを書いて受け渡すだけで完成する

### Unity 版で止まる理由

- C# やシェーダーのコード自体は、スマホアプリの Claude でも Muse でも書ける
- しかし C# はそのままではブラウザで動かない。**Unity 本体で WebGL に変換（ビルド）する工程が必須**
- その Unity が：
  - **スマホアプリの Claude**：会話専用アプリであり、Unity を入れることもビルドを回すこともできない
  - **Muse（nono）**：自分の仮想マシンに Unity が無く、ライセンス認証も含めて実行環境を用意できない
- 結果として、ビルドと、それに伴う「実際に動かして見た目を調整する」反復が両者では回せない

### ブラウザで HD-2D lite 版なら実行できる理由

- ブラウザ自体が実行環境を標準で持っている（HTML / JavaScript / WebGL）。テキストファイルを置けば変換なしにそのまま動く
- HD-2D の見た目は要素に分解すれば WebGL で再現できる：
  - 3Dのジオラマな地形 → Three.js などの 3D 描画
  - ドット絵キャラ → スプライトを板に貼って立てる（ビルボード）
  - 斜めの光と影 → ライティングとシャドウマップ
  - ブルーム、被写界深度 → ポストプロセスのシェーダー
- ただし Unity/URP のような最適化の仕組みが無いため「lite」になる。ぼかしの簡易化、内部解像度の低下、影の軽量化といった割り切りが要り、演出全部盛りはスマホで重い。1シーン試作の規模なら割り切り込みで成立する
- 住み分け：**本格版＝Unity（要ビルド）／ lite版＝ブラウザ標準技術（ビルド不要）**

## 7. リポジトリの分け方と、画像素材の再利用

### 方針：試作は同居、本開発は開発・公開とも専用リポジトリ

| 段階 | 開発（ソース） | 公開先 |
|---|---|---|
| 試作 | Unity プロジェクトは PC ローカル | ビルド成果物だけ `nono-playground/hd2d-test/` に置く |
| 本開発 | 専用リポジトリ（例：`ukos/nono-hd2d`） | 同リポジトリの GitHub Pages で別サイトとして公開（`ukos.github.io/nono-hd2d/`） |

※ 2026-11-18 夜に前倒しで実施済み：専用リポジトリ `ukos/nono-hd2d` を作成し、lite 版を移行した（公開先 https://ukos.github.io/nono-hd2d/lite/ 、旧 `hd2d-test/` は転送ページに置換）。Unity 用スクリプト一式も同リポジトリの `unity-scripts/` に同居させている。

### 公開先（nono-playground）も分ける理由

GitHub Pages は「リポジトリ＝1サイト」の単位だから：

- **サイズ上限がリポジトリ単位**：フォルダ分けしても本編・Stage Actor・HD-2D で同じ上限（1GB目安）を分け合う。HD-2D のビルドは大きく、本編側を圧迫する
- **公開の事故範囲もリポジトリ単位**：フォルダが別でも push や Pages の障害はサイト全体に効く。別リポジトリなら HD-2D の事故が本編に届かない
- **URL も独立**する
- Stage Actor が「開発リポジトリ（nono-stage-actor）／公開先（nono-playground/stage-actor）」に分かれているのと同じ発想で、HD-2D は開発も公開も専用に揃えるのが一貫する
- なお今の nono-playground（本編＋Stage Actor の同居）自体は動いているので、今すぐ分ける必要はない。「HD-2D を3つ目の同居人にしない」という話

### ソースコード側を分ける理由

- Unity のビルド成果物は数十MB級で、差し替えのたびに履歴が太る
- Unity プロジェクトは `Library/` など巨大な生成フォルダを除外する専用の管理が必須で、現行のテキスト中心の運用と混ざると事故の元になる

### 画像素材の再利用ルール

Unity は「プロジェクトの Assets に入れた物しか使えない」ため、参照ではなく**コピーして取り込む**のが前提。その上で：

1. **正本は現行側に1か所だけ**（今のスプライト資産）。HD-2D 側は取り込み時点のスナップショットとして扱う
2. 取り込みは手作業で選ばず、対象フォルダを一括コピーする手順にし、**取り込み記録（元パス・日付・版）をファイルに残す**（「正は保持している版」という従来の教訓と同じ）
3. HD-2D 側で改変した素材は HD-2D 専用として分離し、正本には自動で戻さない
4. シンボリックリンクや git submodule は使わない。Windows＋Unity で事故りやすく、Pages 側の扱いも面倒なため

## 8. 用語と方式の整理（2026-11-18 のやり取りから）

### Three.js と WebGL の関係

- **WebGL**：ブラウザが標準で持つ、3D描画のための低レベルな命令セット（Khronos 策定、OpenGL ES が土台）。GPU へ直接指示を出す層で、そのまま使うとシェーダーや頂点バッファの管理を全部自分で書くことになる
- **Three.js**：WebGL の上に乗る JavaScript ライブラリ。「シーン」「カメラ」「ライト」「素材」という部品で 3D を組み立てられる枠組み
- 関係：**WebGL が土台の描画機能、Three.js はそれを使いやすくした道具**。lite 版は Three.js 経由で WebGL を使っている
- なお Unity の WebGL 出力は Three.js を使わない。Unity は自前エンジンを WebAssembly に変換して WebGL を直接叩く。「WebGL に行き着く道が違う」

### スマホ向けの届け方と、ブラウザ版の2つの作り方

| 届け方 | 中身 |
|---|---|
| アプリ版 | ストアからインストールするネイティブアプリ（Unity 等で制作） |
| ブラウザ版 | URL を開くだけで動く。最終的にはどちらも WebGL で描画する |

ブラウザ版の作り方は2通り：

| 方式 | 作り方 | 特徴 |
|---|---|---|
| lite版（スクリプト版） | HTML/JavaScript＋Three.js で直接書く | 変換工程なし・軽い。スマホアプリの Claude や nono でも制作・公開まで通せる（今回の試作が実例） |
| Unity本格版 | Unity（C#）で作り、WebGL ビルドで変換する | エンジン自体も一緒に変換されるため重いが、本格的な演出と最適化ができる。制作には Unity のある PC が必要 |
